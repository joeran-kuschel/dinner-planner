# Translations (i18n)

The app uses [Lingui](https://lingui.dev) with gettext `.po` catalogs. Messages are written in English in the source,
the catalogs hold one translation per language, and the language is chosen per request on the server. For the user's
view see [Language](../ui/language.md).

## Files

| Path | What it is |
| --- | --- |
| `lingui.config.ts` | Languages (`en` is the source, `de`) and where the catalogs live. |
| `locales/{en,de}/messages.po` | The catalogs. Checked in, edited by hand or in a PO editor. |
| `locales/{en,de}/messages.ts` | Compiled from the `.po` files. Generated, git-ignored, never edited. |
| `lib/i18n/config.ts` | `LOCALES`, `DEFAULT_LOCALE`, the cookie name, `negotiateLocale()`, `createI18n()`. Used by client and server. |
| `lib/i18n/catalogs.ts` | The compiled catalogs, keyed by language. Server side only. |
| `lib/i18n/server.ts` | `getLocale()` and `getServerI18n()` for server components. |
| `app/actions/locale.ts` | `setLocale`, the server action behind the switcher. |
| `components/i18n-provider.tsx` | Gives client components the request's language. |
| `components/language-switcher.tsx` | The switcher in the header. |

## Writing translatable code

Wrap every text the app shows in a macro and pass the i18n instance explicitly:

```tsx
import { plural, t } from "@lingui/core/macro";
import { Trans } from "@lingui/react/macro";

// Server component or page
const { i18n, locale } = await getServerI18n();
t(i18n)`Grocery list`
t(i18n)`from ${plural(count, { one: "# recipe", other: "# recipes" })}`
<Trans>No recipes yet. <Link href="/recipes/new">Add your first one</Link> …</Trans>

// Client component
const { i18n } = useLingui();          // from "@lingui/react"
t(i18n)`Dinner for ${weekday}`
```

- **Always `t(i18n)`, never a bare `t` or `plural`.** Those use Lingui's global instance, which is shared by all requests
  on the server and never activated, so they throw ("without setting a locale"). A `plural` nested inside `t(i18n)` is
  fine.
- **Every server page and layout that shows text calls `getServerI18n()` first.** It also hands the instance to Lingui's
  server `<Trans>`. It is cached per request.
- **Name the placeholders.** `${recipe.name}` becomes `{0}` in the catalog; destructure first (`const { name } = recipe`)
  so translators see `{name}`. The same English text with the same placeholder names is one message, shared by every
  place that uses it.
- **Plurals** use ICU syntax. A German translation may use a plural where English needs none (`Serves {servings}` →
  `{servings, plural, one {Für # Person} other {Für # Personen}}`).
- **Helpers that produce text take the instance:** `formatQuantity(quantity, unit, i18n)`,
  `formatGroceryQuantity(line, i18n)`. Date helpers take the language: `formatWeekday(day, locale)`,
  `formatDayMonth(day, locale)`, `formatWeekRange(weekStart, locale)`. Dates stay pinned to UTC.
- **Server-action errors are messages, not sentences.** `app/actions/recipes.ts` returns a `MessageDescriptor` built with
  `msg` in `RecipeFormState.error`, and the form shows `i18n._(state.error)`. The error is therefore shown in the current
  language and follows a switch while it is on screen.
- User data (recipe names, ingredients, units) is never translated.

## Adding or changing a message

1. Write or change the English text in the code, as above.
2. `npm run i18n:extract` updates both catalogs (`--clean` drops messages that are gone).
3. Fill in the German `msgstr` for every new or changed entry in `locales/de/messages.po`.
4. `npm run i18n:compile` (also run automatically before `dev`, `build`, `typecheck` and the Vitest run).

`i18n:compile` runs with `--strict`: a message without a German translation stops the build and the tests.
`tests/infra/i18n.test.ts` also fails when the catalogs are out of date with the source, when a German message is empty,
or when it drops or renames a placeholder.

## Adding a language

Add it to `locales` in `lingui.config.ts` and to `LOCALES`, `LOCALE_NAMES` and `INTL_LOCALES` in `lib/i18n/config.ts`,
import its catalog in `lib/i18n/catalogs.ts`, then extract, translate and compile as above.

## Choosing the language

`getLocale()` decides once per request:

1. The `locale` cookie, if it names a language the app has.
2. Otherwise the best match for the `Accept-Language` header (`negotiateLocale()`): the browser's languages by their
   `q` weight, regional variants counting for their language (`de-AT` → `de`).
3. Otherwise English.

The root layout sets `<html lang>`, translates the metadata (`generateMetadata`; pages set only their own part of the
title, the layout adds "· Dinner Planner"), and passes only the active catalog to `I18nClientProvider`.

## Switching without a reload

The switcher is a form whose buttons post `locale` to `setLocale`. The action validates the value and sets the cookie:
`path=/`, one year, `SameSite=Lax`, `HttpOnly` (only the server reads it; no `Secure`, since the cluster serves plain
`http://dinner.local`). Setting a cookie in a server action makes Next.js render the current route again and send it
with the action's answer. The browser applies that RSC payload in place: server components come back in the new
language, `<html lang>` and the title update, and the provider switches the client components to the new catalog
without remounting them, so their state and the focus survive. Without JavaScript the form posts normally and the
response is the page in the new language.

## Build and tests

- **Next.js** compiles the macros with `@lingui/swc-plugin` (`experimental.swcPlugins` in `next.config.ts`). The plugin
  is a Wasm binary built against one SWC version and must match the one inside Next.js: **it is pinned to 6.6.0**, the
  newest release that runs on Next.js 16.3 (6.7.0 fails with `swc_plugin_runner` mismatch errors). Check it again on
  every Next.js upgrade: `npm run build` fails immediately if it no longer matches.
- **Vitest** compiles the macros with Lingui's Babel plugin (`tests/support/lingui-macro.mts`), which does not depend on
  an SWC version. `tests/support/compile-catalogs.ts` compiles the catalogs before a run (in one process: Lingui's
  worker threads crash when started from Vitest).
- Component tests render through `renderWithI18n(ui, { locale })` from `tests/support/render.tsx`; server tests get an
  instance from `testI18n(locale)` in `tests/support/i18n.ts`.
- Playwright asks for `en-GB`, so the specs run in English; `tests/e2e/language.spec.ts` covers German, the switch,
  the cookie, the page without JavaScript, and axe on every page in German.
- The Docker image needs nothing extra: `npm run build` compiles the catalogs first (`prebuild`), and the compiled
  catalogs end up in the standalone output like any other module.
